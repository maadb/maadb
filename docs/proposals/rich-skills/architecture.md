# Rich Skills Pack — Architecture and Placement

Status: proposal. Companion to [`README.md`](README.md). Decides **where each
skill lives** and what that placement costs, using the three placement tiers
already implied by the engine's design.

## The three placement tiers

### 1. Managed (shipped with the engine)

Generated by `@maadb/core`, registered in `MANAGED_ARTIFACTS`
(`src/instructions/manifest.ts`), written into each project with a stamp:

```
<!-- maadb:managed name=<artifact> engine=<semver> hash=sha256:<hex> -->
```

Lifecycle: `maad instructions check` classifies each artifact
(`current` / `outdated` / `modified` / `unmanaged` / `missing`);
`maad instructions refresh` rewrites `outdated` and creates `missing`,
and **never** touches `modified` or `unmanaged` without an explicit force.
Boot paths never refresh; scaffolding is create-if-absent. The MCP surface
exposes the same status via `maad_instructions`.

Current members: `MAAD.md`, `_skills/architect-core.md`,
`_skills/schema-guide.md`, `_skills/import-guide.md`.

**A skill belongs here iff all of the following hold:**

- Its content is a function of the **engine version only** — no project
  facts, no live counts, no machine paths (the fully-static contract that
  `MAAD.md` already follows).
- It teaches the **tool surface or engine doctrine**, so it must stay in
  lockstep with tool renames, new parameters, and cap changes — exactly what
  the stamp/refresh mechanism exists to deliver.
- It is useful to **every** project regardless of domain.
- It is public-repo safe by construction (it ships in an npm package).

### 2. Project overlay (`_skills/local/`)

Project-owned files under `_skills/local/`, already taught by `MAAD.md` as
the place for "project-specific guidance." Never generated, never stamped,
never touched by refresh. Versioned in the project's own git history.

**A skill (or skill fragment) belongs here iff:**

- It encodes **domain decisions**: what this project's types and refs mean,
  naming conventions, which ontology conventions the team adopted.
- It would differ between two projects running the same engine version.
- It needs to evolve at the project's pace, not the engine's release pace.

### 3. Host-only (outside the project tree entirely)

Skills installed in the agent host (Claude Code / Cursor / Codex skill
directories), plus anything that renders, serves, or publishes. Never in
this repo, never in the project tree. Detailed in
[`host-boundary.md`](host-boundary.md).

**A capability belongs here iff:**

- It needs facilities the engine deliberately lacks: rendering, browsers,
  HTTP serving, cross-project state, external delivery channels.
- It orchestrates *multiple* tools/products of which MAADB is only one.
- It embodies host-specific conventions (slash commands, subagents,
  host file layouts).

## Placement matrix

| Capability | Placement | Rationale |
|---|---|---|
| Graph/ontology skill (typed refs, promote prose → structure, path-walk recipes) | **Managed** — `_skills/graph-ontology.md` (**shipped 0.15.0**) | Pure tool-surface pedagogy; must track `maad_relationship_paths` contract changes; domain-free |
| Corpus explorer skill (orient in an unfamiliar project) | **Managed** — `_skills/corpus-explorer.md` (**shipped 0.15.0**) | Same: composes `maad_summary`/`maad_schema`/`maad_query`/paths/orphans; domain-free |
| Structure evolution (schema bumps, densification pressure → new ref fields) | **Managed, by extension** — grow `_skills/architect-core.md` + `_skills/schema-guide.md`; **no new artifact** | Evolution guidance already half-lives there (schema-guide § versioning). A third home would fragment it |
| Report/view composition (`maad_join` + `maad_aggregate` → markdown tables/summaries) | **Managed, as recipes inside the two new skills** — not a standalone artifact yet | Composition patterns are small; a standalone report skill should earn its place with usage evidence, mirroring the Tier 2 "provisional composite" rule |
| Project ontology conventions (what `case→client` *means* here, subtype vocabulary, annotation policy) | **Project overlay** — `_skills/local/ontology.md`, authored by agents following the graph skill | Domain decisions; differ per project; must survive engine refresh untouched |
| Import/domain mapping notes (source-ID maps, corpus quirks discovered while exploring) | **Project overlay** — `_skills/local/corpus-map.md`, authored per the corpus-explorer skill | Snapshot of project truth, not engine truth |
| Graph visualization (interactive renderers, GraphViz/Mermaid pipelines beyond inline text, dashboards) | **Host-only** | Pixels and serving are host concerns; core stays lean (`docs/framework.md` § Engine Design Principles) |
| Admin/browse UIs, web apps over a project | **Host-only** | Same |
| Report *publishing* (PDF, HTML, email, external systems) | **Host-only** | Delivery channels are host integrations; the skills stop at markdown |
| Query languages (Cypher/SPARQL-style) | **Nowhere** — explicitly rejected | The LLM is the query planner; bounded primitives + composition are the contract |

Note the deliberate asymmetry: the managed skills may **instruct agents to
create and maintain** the overlay files (`_skills/local/ontology.md`,
`_skills/local/corpus-map.md`). The engine ships the method; the project owns
the results. This is the same relationship `architect-core.md` already has
with `_registry/` and `_schema/`.

## Stamp/refresh implications of growing the managed set

Adding an artifact to `MANAGED_ARTIFACTS` is cheap by design, but has
consequences worth stating before committing:

1. **Existing projects see it as `missing`.** `maad instructions check`
   reports it; the next `maad instructions refresh` creates it. Projects
   that never refresh simply never get it — acceptable, since skills are
   read-on-demand, not load-bearing for the engine.
2. **The generator must be fully static.** No live counts, no paths, no
   project state (the `MAAD.md` rework precedent). Both proposed skills are
   written to this contract.
3. **A rename or removal is forever-ish.** The classifier keys on the stamp
   `name`; renaming an artifact orphans the old file as `unmanaged` on disk.
   So the artifact names (`graph-ontology`, `corpus-explorer`) and paths
   (`_skills/graph-ontology.md`, `_skills/corpus-explorer.md`) should be
   settled at promotion time, not iterated after.
4. **Every engine release re-baselines content.** Because the "current"
   check compares against the live generator, promoted skills join the
   release discipline: editing them means an engine release. That is the
   *point* for tool-surface pedagogy — and the reason domain content is
   banned from managed skills (it would force engine releases for
   project-level edits).
5. **Package size and public exposure.** Generators ship in the npm tarball;
   content must pass public-repo review like any tracked source.

None of these require manifest machinery changes. The lifecycle as built
(states, force semantics, boot-never-refreshes) handles new artifacts as-is.

## What stays out of `@maadb/core` — restated hard lines

Per the accepted decisions for this wave and `docs/framework.md`:

- No graph query language (Cypher/SPARQL or dialects thereof)
- No visualization, rendering, or UI code of any kind
- No new MCP tools for this pack — the skills compose the 0.13/0.14 surface
- No ontology *engine* (inference, reasoners, triple stores) — "ontology"
  in this pack means disciplined use of typed refs + subtypes + overlay
  documentation, nothing more
- No changes to relationship-path traversal semantics or caps

If validation of the skills surfaces a genuinely common deterministic
composition (e.g. "typed neighborhood summary" bundling `maad_get hot` +
`maad_related` + `maad_search`), the existing Tier 2 provisional-composite
process applies — usage data first, engine change second. The skills should
generate that usage data; they must not presuppose the composite.

## Phased delivery recommendation

**Phase 0–2 — complete as of 0.15.0.** Managed generators shipped:
`generateGraphOntologySkill()` / `generateCorpusExplorerSkill()` in
`src/skills/`, registered in `MANAGED_ARTIFACTS`, listed in `MAAD.md`, with
densification notes folded into `architect-core` / `schema-guide`. This
directory is retained as design background and host-boundary notes.

**Historical note — Phase 1 (overlay validation).** The original plan was to
hand-install drafts under `_skills/local/` before promotion. Delivery
skipped straight to managed promotion after review; friction collection now
happens against the shipped managed files + project overlays.

**Historical note — Phase 2 (managed promotion).** Completed in v0.15.0.
Names and paths are frozen from this point
(implication 3 above).

**Phase 3 — host skills (separate repos / skill dirs, no engine coupling).**
Author host-side visualization and report-publishing skills per
[`host-boundary.md`](host-boundary.md) — e.g. a host skill that walks
`maad_relationship_paths` output into an interactive renderer, or one that
publishes `maad_join`-built markdown reports to a delivery channel. These
version independently and never enter this repo.

Phases 1→2 are strictly ordered (promotion freezes names; validation must
precede it). Phase 3 can proceed in parallel with either.
